# Inter-Agent Protocol

This repository uses explicit mailbox files plus explicit tmux doorbells for Claude/Codex coordination.

There is no passive agent-side watcher loop. There is no supervisor session. Quiet means idle unless an explicit tmux doorbell arrives or the agent is actively working approved queue items.

## Non-Negotiable Doorbell Rule

Writing a mailbox file is not communication. A request or response is not sent
until the writer archives it and doorbells the receiver's primary tmux session.

This applies in both directions and to both request and response files:

- Claude writes `.interagent/claude_request.md` -> Claude must run
  `.interagent/send_to_codex.sh`.
- Codex writes `.interagent/codex_request.md` -> Codex must run
  `.interagent/send_to_claude.sh`.
- Claude writes `.interagent/claude_response.md` -> Claude must run
  `.interagent/respond_to_codex.sh`.
- Codex writes `.interagent/codex_response.md` -> Codex must run
  `.interagent/respond_to_claude.sh`.

Do not rely on the other side polling, waiting, noticing file timestamps, or
having a passive watcher. There are no passive watchers. The sender owns the
doorbell. A sender that writes a mailbox file and does not doorbell has not
completed the protocol.

Every response in an active review loop is itself a request for the receiver to
continue the independent adversarial review cycle. Do not send a neutral "FYI"
response in a review loop. The response must carry the consolidated protocol
phrase and the doorbell must tell the receiver to perform the next independent
adversarial review pass until mutual exhaustion closes the loop.

Doorbells remain pointers only. The full request or response still belongs in
the mailbox file, not in the tmux message.

Every helper-generated doorbell must begin with an explicit transport marker so
the receiver does not confuse a protocol doorbell with a normal user nudge:

- `CLAUDE DOORBELL GENERATED BY .interagent/send_to_codex.sh:`
- `CODEX DOORBELL GENERATED BY .interagent/send_to_claude.sh:`
- `CLAUDE RESPONSE DOORBELL GENERATED BY .interagent/respond_to_codex.sh:`
- `CODEX RESPONSE DOORBELL GENERATED BY .interagent/respond_to_claude.sh:`

The marker identifies the helper that generated the tmux input. User-written
messages without one of these markers are not protocol doorbells unless the
user explicitly overrides the protocol for that one message.

## Consolidated Interagent Review Protocol

This section is the review-specific source of truth for inter-agent reviews. A
reviewer should not need to re-read all of `CLAUDE.md` just to perform a review:
the review-relevant mandates are consolidated here.

### Mandatory Review Header

Every inter-agent review request must start with this header:

```md
# ADVERSARIAL REVIEW REQUIRED

PER .interagent/docs/INTERAGENT_PROTOCOL.md (READ IT)

You must perform a fresh adversarial review using **staged context**:

1. **Protocol first:** read the consolidated interagent review protocol enough
   to know the required role, mailbox, progress-log, checklist, and verdict
   rules.
2. **Code-first pass before narrative bias:** read only the Review Seed section,
   then run the seed's `Diff locator` command and any listed file-list/diff-stat
   commands before relying on the sender's explanation. Do not read the sender's
   claims, prior-findings summary, or implementation narrative until after this
   first pass.
3. **Independent failure model:** from the code/diff, list the bug classes you
   expect, run pattern-class scans, and form your own theory of what could
   break.
4. **Context pass:** then read the full request/response/progress log and
   relevant domain docs. Use that context as a map and business contract, not
   as ground truth.
5. **Synthesis pass:** verify prior claims against real code, expand scope
   where the bug class points, audit tests/docs/security/checklist
   requirements, and write findings with file:line references.

Do not confirm prior summaries, prior approvals, or the sender's framing. If
you skip the code-first pass or treat the narrative as truth, the review is
invalid.
```

The send helpers reject review requests missing the required protocol phrase or
the required `Review Seed` section. Response helpers also reject review-loop
responses missing the required protocol phrase. This is intentional: every
review-loop response asks the other agent to continue the adversarial review
cycle, while every review request gives the receiver enough seed context to
start code-first without first reading the sender's narrative.

### Review Standard

A review is not "does the happy path seem to work?" A review is: "what is going
to break this code, and have I proven that it will not?"

1. Read the real code, not summaries. Open the actual source files, Gradle
   modules, Kotlin call graph, Camera2/session paths, math code, tests, and docs. Handoffs,
   summaries, previous approvals, and memory are not sources of truth.
2. Start from suspicion, not trust. Assume the implementation, the request, and
   prior review summaries may be wrong, incomplete, or biased until proven
   against real execution paths.
3. Reproduce before fixing. If acting as implementer on a bug, identify the
   root cause with file:line evidence before writing fix code. A wrong fix that
   passes wrong tests is worse than no fix.
4. Look for failure paths, not just success. Ask what bad input, stale state,
   race, missing data, wrong identity, sibling path, contradictory contract, or
   silent fallback makes the change fail.
5. Run pattern-class scans. Do not inspect only named lines. Search for the
   whole bug class: `catch` blocks, default values that hide failures,
   unguarded permission/media paths, duplicated helpers, stale timestamp
   assumptions, frame/timestamp pairing shortcuts, and repeated capture-session shapes.
6. Follow the code outside the requested files. Shared helpers, fallback paths,
   duplicated logic, and sibling surfaces are in scope when the bug class points
   there.
7. Tests and docs ship with code. Missing tests, stale docs, missing TSDoc,
   stale data-flow/domain docs, or missing functional-test-registry entries
   are review findings.
8. Test quality matters. Changed areas need real assertions on outputs:
   golden-value tests where values are calculated, invariant tests where totals
   or relationships matter, real pipeline/integration tests where data flows
   through multiple stages, error-path tests, and user-flow E2E where UI flows
   changed.
9. Do not mock application logic in tests. Infrastructure stubs are acceptable
   for Android framework/runtime boundaries, but measurement math, calibration,
   timestamp reconciliation, detection, parsing, transformation, aggregation, and trajectory logic must
   run for real unless the dependency would take hours or longer.
10. Security-sensitive changes require security review. Camera permission,
    media import, file access, data exposure, and settings/persistence changes require
    explicit access-control/security thinking, not ordinary feature review.
11. Every review artifact must include a completed `### Review Checklist`
    populated from `docs/REVIEW_CHECKLIST.md`. Missing checklist means the
    review is incomplete. `APPROVED` is invalid with any applicable unchecked
    item.

### Adversarial Independence

The request and prior reviews are maps of explored terrain, not ground truth.

Review quality depends on sequencing, not on starving the reviewer of all
context. Zero context reduces anchoring but loses the business contract. Full
context first preserves the contract but invites checklist-confirmation bias.
The required posture is staged context: inspect the code/diff first, then read
the narrative and domain context, then perform a final synthesis pass over both.

1. For review work, read the changed code/diff before relying on the sender's
   summary. Form your own initial theory of the bug classes.
2. Every review request must include a **Review Seed** section above the
   narrative. The seed may contain only role, changed files, progress-file path,
   diff locator command, and required protocol/checklist reminders. It exists so
   a reviewer can start code-first without being blind to where the code is.
3. Do not read the sender's implementation narrative, prior-findings
   disposition, or "what I verified" section until after the first code/diff
   pass and initial bug-class scan.
4. After the code-first pass, read the full request/response/progress log and
   relevant docs. Domain context is required; it is just not allowed to be the
   first thing that frames the review.
5. Treat prior findings marked "closed" or "approved" as claims to verify
   against the code, not facts.
6. The reviewer's posture is "what did both of us miss?", not "did the other
   reviewer close their list?"
7. Review the bug class, not just the request. If a named file points to a
   shared helper or sibling handler, follow it.
8. Run mechanical scans every review. Single-finding verification is
   insufficient because the previous pass was also bounded by what that reviewer
   thought to inspect.
9. Closure verdicts from another agent never close your walk. Your pass closes
   only when you independently have nothing left to raise.
10. New findings are added to the open list. Do not grade them by whether another
   reviewer missed them.
11. Every pass is a real pass. A prior walk does not reduce your search space.
12. If a prior finding was fixed, verify the fix against the real code.
13. Zero new findings is valid only after the independent walk actually
    happened.

### Measurement Fail-Loud Rules

Measurement calculations must never silently continue when part of the pipeline
fails. A wrong mph value that looks plausible is worse than a visible "No read."

1. Missing, duplicate, or non-monotonic frame timestamps must abort the
   measurement unless the path has a documented, tested reconciliation strategy.
2. Fewer than three valid detections must abort the measurement.
3. Missing or invalid distance calibration must abort mph conversion.
4. Non-finite fit values, excessive residuals, ambiguous blobs, or unproven
   frame/timestamp pairing must return a fail-loud result, not a fallback speed.
5. Measurement aborts must surface actionable UI errors: what failed and how the
   user can retry or recalibrate.
6. Review every `catch`, default value, nullable fallback, and confidence
   threshold in measurement code. If it can hide a wrong speed, it must fail loudly.

### Review Artifact Requirements

Every inter-agent review response must include:

- findings first, ordered by severity, with `file:line` references;
- open questions or assumptions, if any;
- tests/scans actually run, with enough detail to tell what was and was not
  covered;
- a completed `### Review Checklist` from `docs/REVIEW_CHECKLIST.md`;
- exactly one final verdict line: `APPROVED`, `CHANGES_REQUESTED`,
  `NEEDS_DISCUSSION`, or `IMPLEMENTED`.

If a review response does not meet these requirements, it is invalid and must be
redone.

### Progress Logging

Every review round must be logged before sending the response.

1. Reuse the active progress file for the workstream when one exists.
2. Append a new round section; do not rewrite or delete prior rounds.
3. Include timestamp, role, verdict, findings raised with file:line, findings
   closed, findings still open, tests/scans run, and checklist status.
4. Final mutual-exhaustion approval must be logged by both sides before closure
   is considered durable.

## Live Mailboxes

- `.interagent/claude_request.md` — Claude writes requests for Codex.
- `.interagent/codex_response.md` — Codex writes responses to Claude.
- `.interagent/codex_request.md` — Codex writes requests for Claude.
- `.interagent/claude_response.md` — Claude writes responses to Codex.

Doorbells are pointers only. For review-loop messages, the receiving agent must
open the mailbox only far enough to read the adversarial header plus Review Seed
or findings/file-reference surface, then perform the code-first pass before
reading the rest. For non-review messages, the receiving agent reads the mailbox
file in full before acting.

## Broker Closeout Shapes

`close-review` must verify mutual exhaustion against the archived artifacts, not
only against one mailbox pointer.

Two closure shapes are valid:

- Review-request shape: latest request verdict `APPROVED` and latest response
  verdict `APPROVED`.
- Implementer-led shape: latest implementation request verdict `IMPLEMENTED`,
  plus reciprocal archived response artifacts for the same sequence/task where
  implementer -> reviewer and reviewer -> implementer both end in `APPROVED`.

The implementer-led shape is the normal path when Codex implements and Claude
reviews: the original request records the implementation as `IMPLEMENTED`, then
mutual exhaustion is proven by the final reciprocal `APPROVED` responses.

## Session Names

The primary tmux sessions are:

- `codex-speed-ball`
- `claude-speed-ball`

Startup scripts must not launch supervisor sessions. The only current
supervisor exception is the explicit, user-started Claude idle watchdog
(`claude-supervisor-speed-ball`), which sends no mailbox traffic and only
nudges an unchanged Claude pane at the configured interval. Stop helpers may
remove supervisor sessions when they are found.

## Startup

Start Codex:

```bash
./.interagent/start_codex.sh
```

Start Claude:

```bash
./.interagent/start_claude.sh
```

Startup scripts:

- ensure broker state exists,
- start only the primary agent tmux session when missing,
- leave an already-running primary session untouched,
- send a short fresh-start bootstrap to the primary session only,
- do not launch watchers,
- do not launch supervisors.

Start the optional Claude-only idle watchdog when the user explicitly asks for
it:

```bash
./.interagent/start_claude_watchdog.sh
```

## Sending Work

Claude to Codex:

```bash
./.interagent/send_to_codex.sh
```

Codex to Claude:

```bash
./.interagent/send_to_claude.sh
```

Send helpers:

1. verify the request mailbox exists and has real content,
2. archive the request through the broker,
3. clear only the paired response pointer after broker safety checks pass,
4. type a short tmux doorbell into the receiver's primary session.

Never put the full request in the doorbell. Put the real request in the mailbox.

## Sending Responses

Claude response to Codex:

```bash
./.interagent/respond_to_codex.sh
```

Codex response to Claude:

```bash
./.interagent/respond_to_claude.sh
```

Response helpers:

1. verify the response mailbox exists and has real content,
2. archive the response through the broker,
3. clear only the inbound pointer after broker safety checks pass,
4. type a short tmux doorbell into the receiver's primary session.
5. require the consolidated protocol phrase so the receiver is explicitly
   instructed to do the next independent adversarial review pass.

If a response helper fails, stop and investigate. Do not assume passive pickup.

For continuing review loops, the inbound pointer is usually the other side's
latest response (`claude_response` for Codex -> Claude, `codex_response` for
Claude -> Codex). For direct replies to request files, set
`INTERAGENT_CLEAR_POINTER=claude_request` or
`INTERAGENT_CLEAR_POINTER=codex_request` explicitly before running the helper.

## Optional Wait Helpers

- `.interagent/wait_for_codex.sh`
- `.interagent/wait_for_claude.sh`

These are optional caller-side blocking helpers for humans or scripts. They poll response files only when explicitly invoked by a caller; they are not agent work discovery. Agents discover work only from explicit tmux doorbells.

## Required Response Format

Every inter-agent response must end with exactly one verdict line:

- `APPROVED`
- `CHANGES_REQUESTED`
- `NEEDS_DISCUSSION`
- `IMPLEMENTED`

Review artifacts must include a completed `docs/REVIEW_CHECKLIST.md` section.

After writing a response, immediately run the matching response helper. The
response is incomplete until the receiver has been doorbelled. In a review loop,
that response must instruct the receiver to continue with an independent
adversarial review pass under this consolidated protocol.

## Mailbox Safety

Before truncating, overwriting, or blocking on any live mailbox file:

1. Read the current content.
2. If the file is empty or only an HTML-comment stub, it may be cleared or reused.
3. If the file has real content, process or archive it first.
4. If the content does not match the broker's latest archived artifact, stop and investigate.

Never overwrite another agent's work because a new request is ready.

## Queue Rules

The queue keeps agents busy without watcher nudges.

Supported task states:

- `ready` — implementation task is ready to start.
- `in_progress` — implementer owns the task.
- `in_review` — one active review is under way.
- `ready_for_review` — finished work is queued because the reviewer already has an active review.
- `changes_requested` — reviewer found blocking work.
- `awaiting_concurrence` — one side approved and the other side owes the final independent pass.
- `blocked` — no safe progress until a dependency resolves.
- `done` — mutual exhaustion closed.
- `cancelled` — deliberately abandoned.

Reviewer rule:

- one active review per reviewer.
- additional finished work waits in `ready_for_review`.
- queued review work is promoted only after the active review closes.

Implementer rule:

1. Send one finished subtask for review.
2. Mark that subtask `in_review`.
3. Immediately after doorbelling a review request or review-loop response,
   review the approved plan/progress backlog and identify work that is
   independent of the subtask currently under review.
4. Start the next safe independent task instead of idling. The goal is to have
   another completed subtask ready for review when the reviewer is free.
5. "Independent" means not blocked by the active review result and not editing
   the same write surface in a way that would conflict with likely review
   changes. If no safe independent task exists, record that in the progress file
   before waiting.
6. If independent work finishes while the reviewer is still busy, mark it
   `ready_for_review`; do not start a second active review with the same
   reviewer.
7. A doorbelled review response always takes precedence over ahead-of-current
   parallel work. Treat the response as an interrupt for the current review loop:
   stop at a safe point, log where the parallel work paused, process the
   response, implement/fix/answer as required, write the response, and doorbell
   it back.
8. After doorbelling that response, return to the approved backlog/paused
   parallel task and continue the rolling pipeline.

## Review Closure

One approval is not closure.

The loop closes only when:

1. one side approves,
2. the other side performs one more independent pass,
3. the other side also approves with no new findings.

If either side finds a new issue, the loop continues.

## Obsolete Surfaces

Legacy watcher instruction files, idle-nudge scripts, and external review-watcher stacks are not part of the live protocol. After all live references are removed and reference scans pass, delete obsolete watcher surfaces rather than keeping protocol redirects.
